# Coreweaver Labs — Keyword Cloud and Content Silo Expansion

**Status:** Planning and source record. This is not a keyword-volume forecast, a ranking prediction, an AI-citation strategy, or publication authorization. It maps recurring buyer language to useful public decisions and preserves the project’s existing source, claim-review, and human-publication gates.

## Operating Thesis

Coreweaver’s keyword cloud should grow by **decision depth**, not by manufacturing a page for every phrasing variant. Google’s current guidance emphasizes original, people-first content with clear authorship, useful organization, and descriptive links; it warns against mass production, automation intended to manipulate ranking, or new content added merely to appear “fresh.” [1] [2] Google also states that AI features use the same foundational SEO practices, and that there are no special technical requirements or special markup required beyond indexed, snippet-eligible pages. [3] [4]

> **Editorial rule:** A cloud term earns a public route only when it represents a distinct mid-market B2B reader decision, has a source plan, adds a non-commodity contribution, can receive a parent link plus a contextual inbound link, and carries a specific boundary.

## Measurement and Review Loop

After the canonical domain is verified in Search Console, use the Performance report to review query, page, country, device, click, impression, CTR, and average-position data as observations—not verdicts. [5] Google recommends checking Search Console around monthly or when material content changes, and using its indexing, URL inspection, sitemap, and performance reports to investigate technical and content conditions. [6]

If generative-AI reporting is available for the property, treat it as a visibility record for URLs, impressions, country, device, and date; the 2026 reports are rolling out only to a subset of sites. [7] Do not infer AI-citation quality, reader trust, commercial value, or a causal effect from one report or one period.

| Review question | Evidence to inspect | Safe action |
|---|---|---|
| Is a published guide discoverable? | Index status, sitemap state, raw SSR content, and at least two contextual inbound links | Fix technical or internal-link gaps before creating another page. |
| Is the cloud surfacing a distinct buyer question? | Search Console query/page patterns, support triage, field briefs, and manual audience research | Draft one bounded brief or retain the signal privately. |
| Is a page now duplicative or stale? | Current source, page purpose, claim ledger, named owner, and evidence boundary | Update, merge, qualify, redirect/canonicalize where appropriate, or retire. |
| Is an AI-representation concern supportable? | Public page, exact observed wording/context, source-of-truth comparison, and current policy | Create a private review record; do not promise a platform change. |

## Publication Gate for Every New Cloud Term

1. Write the reader decision, audience/moment, evidence class, boundary, and next route.
2. Create a source plan and claim ledger before drafting.
3. Confirm that the resource is distinct from existing pages and is not a long-tail variation page.
4. Add parent, relevant sibling, method/research, and appropriate service links in meaningful context.
5. Add visible author/reviewer/method information when the page is an Insight or field brief.
6. Validate SSR title, canonical, structured data, visible sources, sitemap coverage, desktop/mobile presentation, focused tests, type checks, and production build.
7. Record the source contract, boundary, validation, and next safe decision in the handoff.
