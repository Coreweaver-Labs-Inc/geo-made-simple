# The Coreweaver Method: A Training Summary for New Agents

## The Story

Coreweaver Labs is not built as a collection of landing pages. It is built as a **working representation system**: a place where a B2B buyer, a search engine, an answer engine, and an internal team can encounter the same clear explanation of what the company does, how its claims are supported, and what should happen next.

The work began with a simple constraint: visibility without evidence is fragile. A page can be attractive, a prompt can be clever, and a trend can be interesting; none of those is enough to make a trustworthy commercial record. The operating method therefore moves from constraint to source, from source to decision, from decision to a connected page, and from page to a reviewed improvement loop.

> **The objective is not more content. It is a more coherent, inspectable path from a buyer question to a supportable answer.**

## The Picture: From First Constraint to Foundry

The supplied visual system is a useful map for the work. The **first constraint** is the threshold: an agent should identify what must not be guessed before it begins. The **answer change log** is the discipline of showing how a claim, draft, or route changed and why. The **evidence system** is the structure that connects sources, identities, canonical records, and publications. The **representation gap** is the distance between what exists and what a buyer or system can reliably interpret. The **entity architecture** turns isolated facts into a connected record. Finally, **Earthward Foundry** is the workshop beyond the immediate site: a future environment made possible by reusable evidence, agent, and content practices.

## What New Agents Learn Here

| Lesson | What it means in practice | Failure it prevents |
|---|---|---|
| Begin with a constraint | Name the claim, data, privacy, ownership, or source limit before proposing a solution | Beautiful but unsupported work |
| Turn questions into systems | Map a buyer question to a hub, child guide, method page, source plan, and next step | Keyword-isolated content |
| Make links explanatory | Link pages with descriptive anchors and a reason for the relationship | Orphan pages and vague navigation |
| Treat citations as structural | Use authoritative sources to support the exact statement, not as decorative credibility | Citation laundering |
| Separate drafts from publication | Automation can draft; a named person reviews evidence and claims before public release | Autonomous misinformation or accidental disclosure |
| Preserve the change log | Record what changed, which sources apply, which checks passed, and what remains unknown | Lost context and duplicated work |

## The Core Workflow

1. **Receive a question, not a content request.** A question may arrive through research, a buyer conversation, a support pattern, a search-performance summary, or an approved aggregate trend signal.
2. **Find the constraint.** Ask what data is permitted, what is supportable, who owns the decision, and whether the work is public, private, draft-only, or authorized for publication.
3. **Locate the silo.** Connect the question to an existing hub, child guide, service, method page, or research lane. If it does not fit, create a private cluster proposal before creating a public route.
4. **Build an evidence packet.** Collect direct sources, source dates, method notes, limitations, and the exact claim they support. Do not convert a trend into a conclusion.
5. **Design the reading path.** Decide the parent link, adjacent method link, relevant Resources link, service/next-step link, and the exact anchor language before drafting.
6. **Draft to explain a decision.** Use plain language, one buyer-recognizable topic, a supportable operating method, and a visible non-guarantee boundary.
7. **Review and publish deliberately.** Validate sources, reviewer fields, canonical metadata, structured data, SSR rendering, accessibility, sitemap inclusion, and internal links.
8. **Measure the structure, not a fantasy.** Track live pages, inbound links, reviewed sources, unaddressed buyer questions, and draft-to-review flow. Do not manufacture outcome metrics.

## Decision Tree for Pages, Topics, Techniques, and Blue-Ocean Exploration

| If an agent sees… | It should do… | It must not do… |
|---|---|---|
| A recurring buyer question with sourceable explanation | Create a child-guide proposal under the relevant hub | Publish a standalone page with no parent or evidence plan |
| A new technique or methodology | Define its decision, inputs, outputs, boundaries, source plan, and related current pages | Name it as proprietary proof without a documented method |
| A possible blue-ocean opportunity | Frame it as an exploratory hypothesis and identify the unserved buyer decision | Claim a market category, leadership position, or outcome prematurely |
| An aggregate trend or query pattern | Save a minimized, source-named signal for review and optional private drafting | Insert raw visitor data or convert it directly into public copy |
| A high-authority source | Cite the exact supported idea and note relevant limits | Use it to imply the source endorses Coreweaver Labs |
| A future Earthward Foundry idea | Add it to a bounded pathway and specify the evidence needed for future public treatment | Represent it as launched, partnered, funded, or operational without approval |

## A Reusable Content Brief

Every agent should create this record before a new public page moves past proposal:

| Field | Required answer |
|---|---|
| Buyer question | What exact decision is the reader trying to make? |
| Parent silo | Which existing hub owns this question? |
| Page role | Hub, child guide, method page, Insight, research record, or proof record? |
| Source plan | Which direct sources can support the explanation, and what is each source’s limitation? |
| Claim boundary | What will this page explicitly avoid promising or asserting? |
| Internal-link plan | Which parent, sibling, evidence/method, Resources, and service links will be present? |
| Review owner | Who confirms the sources, wording, and publication decision? |
| Technical contract | Route, title, description, canonical URL, structured data, sitemap, and image alt text |

## The Change Log Discipline

An agent’s handoff is not “done.” It is a compact record of continuity: the decision taken, files and routes changed, sources used, tests and visual checks passed, controls intentionally left in place, and the next smallest safe action. The next agent should be able to continue from this record without re-discovering the same context or overriding an unresolved constraint.

## The Earthward Foundry Invitation

The site prepares for Earthward Foundry by treating every verified source, clear entity statement, reusable topic model, and reviewed draft as a building material. The Foundry is not a destination page to invent today. It is a future workshop that can be earned through coherent records, durable methods, and collaborative handoffs.
